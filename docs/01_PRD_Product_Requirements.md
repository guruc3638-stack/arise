# 01: Product Requirements Document (PRD)

**Product:** ARISE  
**Version:** 1.0 | **Date:** 21 October 2026 | **Status:** Draft baseline  

## 1. Product summary
ARISE is a student-focused learning and DSA practice platform. It combines structured courses, problem practice, verified DSA XP, leaderboards, a friends comparison view, profile achievements, and personal study-material/time tracking.

## 2. Problem statement
Learners use separate sites and tools to learn programming, practise DSA, track progress, and compare results. ARISE aims to bring progress tracking and competition into one consistent experience while preventing XP farming.

## 3. Product goals
1. Give each registered user a persistent profile and unique ARISE UID.
2. Provide a clear dashboard for the five major areas.
3. Award competitive XP only for verified, correct DSA solves and only once per problem per user.
4. Support global rankings and a separate friends comparison view.
5. Track self-study time and PDFs without awarding XP.
6. Track course lessons and require an 80% final-test score for completion.
7. Record achievements and unlock dates.

## 4. Non-goals / excluded scope
No fitness features, activity verification, exercise detection, messaging/chat, GPS-based features, wearables, AI coach, XP from self-study, self-reported XP, or unrelated gamification systems. Do not add a standalone friends social network; friends comparison is ranking-only.

## 5. Target users
- Learner: practises DSA, takes courses, tracks personal progress.
- Friend/peer: appears in the comparison view when eligible under the chosen friend relationship model.
- Administrator/operator: maintains course content, problem catalogue, and operational settings. Admin capabilities should be restricted to what is needed to operate the defined product.

## 6. Product navigation
Dashboard → Leaderboard | DSA | Self Study | Learning | Profile.  
Friends comparison is a view within Leaderboard, not a new top-level dashboard section.

## 7. Functional requirements

### FR-01 Authentication and profile
- Users can sign in and complete a profile.
- Profile stores display name/hunter name and unique UID.
- Profile displays overall progress, skill/category progress, badges, completed skills/courses, and rank where available.
- User can control visibility of DSA rank/progress.
- UID is generated by the system and unique; it is not a secret or authentication credential.

### FR-02 Dashboard
- Dashboard links to the five major sections.
- Dashboard shows summary values only when backed by persisted data; do not show fabricated statistics.

### FR-03 DSA catalogue and practice
- Browse problems by topic and difficulty.
- Problem metadata includes title, source, official URL, topic, difficulty, and whether it is available for in-platform judging or external practice.
- For in-platform judged problems, user submits code and receives a verdict from a trusted backend judge.
- For external links, user may open the official source, but an outbound click is not proof of a correct solve.
- Maintain separate unique-solved and practice counts.

### FR-04 XP rules
- XP is awarded only after a correct, verified submission.
- Each user/problem pair can receive XP at most once.
- Later successful attempts may increment practice count but award zero additional XP.
- XP values come from a versioned, predefined table based on the agreed topic/difficulty rules; the client cannot choose or modify XP.
- XP ledger is append-only or otherwise auditable. Duplicate requests must not duplicate awards.
- Self Study, course completion, manual claims, and external-link clicks do not award DSA XP unless a separately approved rule explicitly changes this baseline.

### FR-05 Leaderboard
- Show college, district, Maharashtra/state, and India rankings.
- Ranking score is verified DSA XP only.
- Ranking scope and user eligibility must be explicit.
- Handle ties deterministically; tie-breaker is TBD in decision log.
- Do not expose hidden DSA rank/progress to users who are not allowed to see it.

### FR-06 Friends comparison
- Provide a separate friends comparison view inside Leaderboard.
- Compare eligible friends using verified DSA XP and appropriate profile/rank data.
- This feature does not include chat, direct messaging, or a social feed.
- Friend relationship/invitation model is TBD before implementation.

### FR-07 Self Study
- Users can upload and manage permitted PDF study material.
- Track study sessions/time for personal insight.
- Study time is personal tracking only and never contributes to XP or rankings.
- Enforce file type/size limits, ownership checks, and safe storage.

### FR-08 Learning
- Courses contain lessons and a final test.
- Course completion requires a final-test score of at least 80%.
- 100% lesson progress alone does not mark a course complete.
- A failed test may be retaken subject to a configurable policy; retake policy is TBD.
- Successfully completed courses/skills appear on profile.

### FR-09 Badges
- Unlock badges from defined achievements only.
- Store badge identifier and unlock timestamp/date.
- Prevent duplicate badge awards.

## 8. Key success criteria
- No duplicate XP for the same user/problem pair, including concurrent submissions.
- All leaderboard totals equal the sum of verified XP ledger entries.
- Self Study sessions never affect XP.
- A course is completed only if the recorded final score is >= 80%.
- User data and PDFs are private by default and ownership-checked.
- Users can find their current rank and understand the ranking scope.
- No unauthorized third-party problem content is copied into ARISE.

## 9. MVP acceptance criteria
MVP is acceptable when authentication/profile, DSA problem flow for authorized/original problems, one-time XP, leaderboard scopes, friends comparison, self-study PDF/time tracking, course tests/80% completion, profile achievements, and automated tests work end-to-end in a deployed test environment.

## 10. Assumptions and constraints
- Proposed stack: React + Vite + Tailwind, FastAPI, PostgreSQL/Supabase.
- Third-party platform API/verification access is not assumed.
- College/district/state fields require validation and a clear source of truth.
- Privacy, retention, age requirements, and public profile visibility require a policy before public launch.
